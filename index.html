What leading an ITSM migration taught me about the small details

Ziad Dwagy · ITSM Team Lead · Dubai

This month we went live on a new ITSM platform. We moved from IFS Assyst, a tool I had owned and shaped for years, to ManageEngine. I led the migration tasks and spent two months supporting the go-live, including evenings and weekends with the team.

Migrations get described as data moving from one system to another. In practice, the data is the easy part. The hard part is everything the old system was quietly doing for you that nobody wrote down. Here are the lessons I'm taking with me.

1. Map the behaviour, not just the fields

Our old platform enforced rules in places nobody remembered: a priority matrix in one table, contract checks in a lookup filter, SLA timing tied to service hours. Field mapping alone would have lost all of that. Before moving anything, list what the old system does: what it blocks, what it calculates and what it triggers. Then decide where each behaviour lives in the new platform.

2. SLAs follow the clock, so define the clock first

Our BFSI customers run sites on very different schedules: some 24×7, some 15 hours a day for five days, others 13 hours a day all week, plus standard office hours. In ServiceDesk Plus MSP, operational hours per site turned out to be the right key for SLA behaviour. Get the calendars right first and the SLAs follow. Get them wrong and every report afterwards is wrong too.

3. Multi-tenant means isolation by design

When one platform serves several customer accounts, isolation has to be designed in. We found that categories are scoped at the account level, not the site level. That meant separate category trees per account, which was cleaner than trying to share one and filter it.

4. Some problems are platform limits, not configuration mistakes

We wanted tickets to fill in product and contract details automatically from the selected asset. After a lot of testing it became clear the asset field simply isn't available to client-side form rules in this edition. Recognising a platform limit early saves days. We moved the logic to server-side custom triggers instead.

5. Infrastructure details can stop a project cold

Two examples. Our database migration failed until we recreated the database with the collation the application expected. Later, one user couldn't connect at all, and the cause was antivirus SSL inspection, not our certificate. Neither is glamorous, but both blocked progress until someone dug in.

6. Validation belongs where the user actually submits

On the old platform I built a database trigger to block tickets for items without a valid maintenance contract. It worked perfectly when tested directly in SQL, but the application validated input before it ever reached the database. The lesson: enforce rules at the layer the user goes through, and test through the real front end.

7. Monitoring and SLAs need to agree

In Zabbix, putting a host into maintenance doesn't automatically exclude that downtime from SLA calculations. Those are two separate settings. Alerts can also still fire during maintenance unless the notification actions are set up to ignore it. Planned work should never damage your availability figures, so check both.

8. Reporting is part of the service

I built a live service dashboard covering incidents, requests, SLAs and engineer performance, and embedded it in the ITSM portal so people didn't have to go looking. Along the way I fixed a reporting query that pushed the database server to 100% CPU, by splitting it into targeted queries and pre-aggregating joins. A dashboard nobody trusts, or one that slows the server down, doesn't help anyone.
